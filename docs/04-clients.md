# 4. Calling the server

TF Serving has five things you can ask it: **Predict**, **Classify** and
**Regress** run a model; **GetModelMetadata** describes one; and
**GetModelStatus** reports what's loaded. This chapter shows each one from
the three clients in the repo and from curl.

## The clients

`python/`, `go/` and `rust/` hold the same client in three languages. None
of them hard-codes a model: requests are built from JSON at runtime
([chapter 5](05-requests-and-responses.md)), so one binary can call any model.

```
client <command> [flags]

commands   predict | classify | regress | metadata | status
flags      --addr host:port   (localhost:8500)
           --model NAME       (demo)
           --version N        a specific version        } at most one;
           --label NAME       a version label           } default: latest
           --timeout SECONDS  (10)
predict, classify, regress only:
           --signature NAME   (serving_default)
           --input FILE       JSON request; - = stdin (default)
```

They log what they send and which servable answered to **stderr**, and print
the result as JSON on **stdout**, so `| jq` works. Exit status: `0` ok, `1`
the RPC failed, `2` bad arguments or bad input.

Setup:

```bash
# Python 3.10+, in a virtualenv
python3 -m venv .venv && .venv/bin/pip install -r python/requirements.txt
PYTHON=.venv/bin/python ./python/gen_protos.sh   # writes python/gen/ (no TensorFlow needed)
.venv/bin/python python/client.py status --model demo

# Go 1.24+ (generated code is committed)
cd go && go run ./cmd/client status --model demo

# Rust: a current stable toolchain (`rustup update`); 1.76 is too old.
# Stubs are generated by build.rs with a vendored protoc.
cd rust && cargo run -- status --model demo
```

`scripts/e2e.sh` (`make e2e`) runs every command in all three languages
against a live server and checks they print the same JSON.

## predict: run a signature on tensors

```console
$ python python/client.py predict --input examples/applicants.json
input  age: DT_INT64 [3]
input  city: DT_STRING [3]
input  embedding: DT_FLOAT [3, 3]
input  income: DT_FLOAT [3]
model demo version 2 signature serving_default
output label: DT_STRING [3]
output score: DT_FLOAT [3]
{
  "outputs": {
    "label": ["approve", "review", "approve"],
    "score": [0.66907406, 0.3188647, 0.80767924]
  }
}
```

(JSON arrays are condensed in these docs; the clients print one element per
line.)

The same request to the `stable` label goes to version 1, which has
different weights:

```console
$ python python/client.py predict --label stable --input examples/applicants.json 2>/dev/null | jq -c .outputs.score
[0.73885,0.31216973,0.8263534]
```

Over REST, the same request is a JSON body, and the server converts it using
the signature:

```bash
curl -s localhost:8501/v1/models/demo:predict -d '{
  "inputs": {"age": [34, 51], "income": [72000.0, 38000.5],
             "city": ["Austin", "Dallas"], "embedding": [[1, 0, 0], [0, 4, 0]]}}'
```
```json
{"outputs": {"label": ["approve", "review"], "score": [0.669074059, 0.318864703]}}
```

| | REST URL |
|---|---|
| default signature, latest version | `POST /v1/models/demo:predict` |
| other signature | add `"signature_name": "half_plus_two"` to the body |
| version / label | `/v1/models/demo/versions/1:predict`, `/v1/models/demo/labels/stable:predict` |

To keep only some outputs, the gRPC request has
`output_filter: ["score"]`.

## classify: labels and scores from tf.Examples

Classify sends a list of `tf.Example`s (feature name → values) and gets back,
for each example, a list of `(label, score)` pairs. The model must have a
classify-shaped signature ([chapter 1](01-models.md#exporting-classify-and-regress-signatures)).

```console
$ cat examples/iris_classify.json
{
  "examples": [
    {"sepal_length": 5.1, "sepal_width": 3.5, "petal_length": 1.4, "petal_width": 0.2},
    {"sepal_length": 5.9, "sepal_width": 3.0, "petal_length": 4.2, "petal_width": 1.5},
    {"sepal_length": 6.3, "sepal_width": 3.3, "petal_length": 6.0, "petal_width": 2.5}
  ]
}
$ python python/client.py classify --model iris --input examples/iris_classify.json
input  3 examples (petal_length:float, petal_width:float, sepal_length:float, sepal_width:float)
model iris version 1 signature serving_default
{
  "classifications": [
    [{"label": "setosa", "score": 0.9878716}, {"label": "versicolor", "score": 0.012128434}, {"label": "virginica", "score": 6.760278e-09}],
    [{"label": "setosa", "score": 0.0010766457}, {"label": "versicolor", "score": 0.96666265}, {"label": "virginica", "score": 0.032260675}],
    [{"label": "setosa", "score": 1.495605e-08}, {"label": "versicolor", "score": 0.01798621}, {"label": "virginica", "score": 0.98201376}]
  ]
}
```

REST (`examples` takes the same JSON):

```console
$ curl -s localhost:8501/v1/models/iris:classify -d @examples/iris_classify.json
{"results": [[["setosa", 0.987871587], ["versicolor", 0.0121284341], ["virginica", 6.76027812e-09]], ...]}
```

Features shared by every example can go in a `context` object, sent once
instead of repeated:

```bash
curl -s localhost:8501/v1/models/iris:classify -d '{
  "context":  {"sepal_length": 5.0, "sepal_width": 3.0},
  "examples": [{"petal_length": 1.4, "petal_width": 0.2},
               {"petal_length": 5.5, "petal_width": 2.0}]}'
```

The gRPC clients accept the same `context` key.

## regress: one number per example

```console
$ python python/client.py regress --model iris --signature regress --input examples/iris_regress.json
input  3 examples (petal_length:float)
model iris version 1 signature regress
{"regressions": [0.21940002, 1.509, 2.1330001]}

$ curl -s localhost:8501/v1/models/iris:regress -d '{"signature_name": "regress", "examples": [{"petal_length": 1.4}]}'
{"results": [0.219400018]}
```

Calling an API with a signature of the wrong kind is rejected:

```
error: Classify failed: INVALID_ARGUMENT: Expected classification signature outputs
to contain at least one of "classes" or "scores". Signature was: ...
```

## metadata: what does the model expect?

`GetModelMetadata` returns every signature with its inputs and outputs: the
same information as `saved_model_cli`, but from the running server. Use it
to check a deployment, or to build requests generically.

```console
$ python python/client.py metadata --model iris
model iris version 1
{
  "signatures": {
    "classify": {
      "method": "tensorflow/serving/classify",
      "inputs":  {"inputs": {"dtype": "DT_STRING", "shape": [-1]}},
      "outputs": {"classes": {"dtype": "DT_STRING", "shape": [-1, 3]},
                  "scores":  {"dtype": "DT_FLOAT", "shape": [-1, 3]}}
    },
    "predict": {
      "method": "tensorflow/serving/predict",
      "inputs":  {"features": {"dtype": "DT_FLOAT", "shape": [-1, 4]}},
      "outputs": {"class_id": {"dtype": "DT_INT64", "shape": [-1]},
                  "probabilities": {"dtype": "DT_FLOAT", "shape": [-1, 3]}}
    },
    "regress": { ... },
    "serving_default": { ... }
  }
}
```

`shape` is `-1` for an unknown dimension, and `null` when even the rank is
unknown (`demo`'s `half_plus_two` accepts any shape). TF2 models also list
`__saved_model_init_op`, which is internal.

On the wire, the response's `metadata` map holds a `google.protobuf.Any`
that wraps a `SignatureDefMap`. Each client unpacks it (see
`responses.py` / `responses.go` / `responses.rs`). REST returns the same
thing as JSON at `GET /v1/models/iris/metadata`, including internal tensor
names.

## status: what's loaded?

```console
$ python python/client.py status --model demo
{
  "versions": [
    {"version": 2, "state": "AVAILABLE", "error_code": "OK", "error_message": ""},
    {"version": 1, "state": "AVAILABLE", "error_code": "OK", "error_message": ""}
  ]
}
$ curl -s localhost:8501/v1/models/demo          # REST equivalent
$ curl -s localhost:8501/v1/models/demo/versions/1
```

Status lives on a different gRPC service, `tensorflow.serving.ModelService`,
on the same port. It takes `--version` but not `--label`: the server
ignores labels here and lists every version, so the clients refuse
`status --label`.

[Chapter 2](02-loading.md#model-status-is-it-loaded) explains the states.

## Errors

Every failure is a gRPC status code (REST maps them to HTTP codes). The
ones you will meet:

| gRPC code | REST | typical cause |
|---|---|---|
| `INVALID_ARGUMENT` | 400 | wrong dtype (`expected float, got int64`), missing input, unknown signature or label, wrong API for the signature, scalar input with batching on |
| `NOT_FOUND` | 404 | unknown model, or version not loaded |
| `FAILED_PRECONDITION` | n/a | label on a version that isn't loaded (config reload) |
| `UNAVAILABLE` | n/a | server down, wrong `--addr`, or the batching queue is full |
| `DEADLINE_EXCEEDED` | n/a | the client's `--timeout` expired (REST: `--rest_api_timeout_in_ms`) |
| `RESOURCE_EXHAUSTED` | n/a | message over gRPC's 4 MB default limit |

`INVALID_ARGUMENT`, `NOT_FOUND` and `FAILED_PRECONDITION` are bugs on the
caller's side, so don't retry them. Retry `UNAVAILABLE`, with backoff.
